# 축 상호작용 설계 (결과 개념은 결합의 패턴이다)

작성일 2026-11-03 · 상태: **초안 (제안)**. 축의 이름과 가족은 `축과-층위.md`에서 이미 정했다. 이 문서는 **축들이 서로 어떻게 맞물리는가**를 다룬다.

---

## 1. 문제

축은 정해졌지만, 축끼리 맞물리는 방식이 흩어져 있었다 (접촉 전달, 규칙 사슬, 속도 법칙, 번짐, 지각 임계). 지금까지 만든 개념들 — 잔류, 손상, 자국, 냄새, 번짐, 내구 — 은 모두 이 결합의 **결과에 붙인 이름**이다. 결합 자체가 정의되지 않으면 새 결과 개념을 추가할 때마다 엔진이 바뀐다.

## 2. 제안: 엔진이 아는 결합은 다섯 종류뿐이다

| 결합 | 뜻 | 이미 있는 것 |
|---|---|---|
| **접촉 전달** | 두 개체가 면으로 닿으면 양이 옮겨진다 | `contact` 사전, 전달률(천분율) |
| **규칙 사슬** | 상태 조건이 맞으면 다른 상태가 생긴다 | `rules`, `canLink`, 단계 키 조건 |
| **누적** | 노출량이 속도(축 입력의 곱)에 따라 쌓이고 임계에서 단계가 오른다 | 속도 법칙(축과-층위 8) |
| **지각** | 상태가 인물의 감각 임계를 넘으면 인물에게 보인다 | 감각 사전, 인지 단계 |
| **행동** | 인물의 동사가 상태를 바꾼다 (효과 요청) | `action` 사전, `offers` |

- 규칙 사슬과 접촉 전달은 **물체 ↔ 물체**, 지각과 행동은 **인물 ↔ 물체**다. 누적은 **시간**과 물체를 잇는다.
- 다섯 결합 밖의 것은 엔진에 넣지 않는다. 필요해 보이면 기존 다섯 중 하나의 조합으로 표현되는지 먼저 본다.

## 3. 결과 개념은 결합의 패턴이다

| 결과 | 결합 조합 | 축 |
|---|---|---|
| **잔류** (진물, 물기) | 접촉 전달로 옮겨짐 → 젖음 축이 누적 감소(마름) → 고착 | 젖음, 잔류 |
| **손상** (터짐) | 곰팡이 누적 → 가공 계수 → 임계 넘으면 터짐 | 곰팡이, 손상 |
| **자국** (고정) | 잔류 고착 **그리고** 재질의 얼룩 특성 → 고정 상태로 전이. 행동으로만 소멸 | 잔류, 자국, 재질 특성 |
| **냄새·번짐** | 원천 상태 → 공기 매질 규칙 → 인접 장소로, 거리에 따라 약해짐 | 냄새, 장소 그래프 |
| **벌레** | 냄새 규칙 → 자력 이동 매질 → 원천 쪽으로 이동 | 벌레 |
| **내구** | 손상 누적 × 부위 배율 (나중에) | 내구, 손상 |

즉 **잔류·손상·자국·냄새·벌레는 새 결합이 아니다.** 다섯 결합의 조합이다. 새 결과 개념은 조합을 한 줄 더하는 것이지 엔진을 고치는 것이 아니다.

## 4. 물리 질서 (정한 것 같은데 명시가 없던 것)

1. **보존**: 접촉 전달은 양을 **옮길 뿐 만들지 않는다.** 한쪽이 줄면 다른 쪽이 늘고, 나머지는 소멸(고정 → 소멸 전이, 흡수, 증발)로만 나간다. 이것이 "들어온 양 = 이동 + 소멸"의 수지 검사다 (수지 검사는 아직 없다).
2. **원천 없으면 번지지 않는다**: 번짐 개체는 원천 상태 없이는 존재하지 않는다 (`needs`). 원천을 치우면 번짐이 **부재 보정**으로 천천히 줄어든다.
3. **단계는 한꺼번에 갱신한다**: 한 단계 경계에서 모든 규칙을 직전 값으로 읽고 한꺼번에 쓴다. 규칙 순환(곰팡이 가속)이 자기 값을 다시 읽지 않게 하는 장치다 (축과-층위 8).
4. **시간은 이벤트로 진행한다**: 매 틱 전체를 훑지 않는다. 상태 변화 시각은 직전 스냅숏에서 누적 식을 풀어 구한다 (속도 법칙의 도달 시간 = 임계 ÷ 속도). 부재 중에는 같은 식을 큰 간격으로 한 번에 적용한다 (상한 있음).

## 5. 작가에게 묻는 결정 (4개)

1. **보존을 엔진 규칙으로 강제할까?** 전달은 항상 양을 옮기고, 자국·잔류는 원천에서 빠져나간 양과 같아야 한다. 권장: 예 (수지 검사 추가). 이 검사가 있으면 "소멸"의 뜻이 정확해진다.
2. **시간은 이벤트 기반으로 할까?** 권장: 예. 매 틱을 돌리지 않고 상태 변화 시각을 예약한다. 부재 보정과 같은 식을 쓴다.
3. **한 행동이 여러 축을 움직일 때**: 한 단계씩 순서대로 적용할지, 한꺼번에 적용할지. 권장: 한꺼번에 (4-3).
4. **재질 특성은 결합에 어떻게 들어가나?** 권장: 특성은 접촉 전달의 전달률과 누적 속도의 **가속 항**에만 들어간다. 새 결합 종류를 만들지 않는다. (자국 = 고정 전이를 얼룩 특성이 게이트하는 것)

## 6. 다음 작업 제안

- 결정 1·2가 확인되면 `docs/상호작용-명세.md` 3장과 `축과-층위.md` 8장을 이 문서의 결합 다섯 가지로 맞춘다.

## 8. 판정 규칙 (2026-11-03, 작가 승인)

- **결정론**: 지연 발화와 행동 비용은 결정론으로 정한다. 같은 입력이면 같은 결과다.
- **확률의 자리**: 확률은 "벌레가 얼마나 꼬이나" 같은 **이벤트 발생**에만 쓴다. 상태 변화와 판정 결과에는 쓰지 않는다.

## 9. 지연 (예약 판정)

규칙에 지연 필드를 붙인다. 원인 조건이 성립하면 예약이 생기고, 시간이 지나 발화 시점에 **조건을 다시 판정한다.**

```yaml
rules:
  bugs_swarm_after_rot:
    label: 상한 음식을 오래 두면 다음 날 벌레가 들끓는다
    on: [OBJ+1|body:rot@>=spoiled]
    delay_s: 28800          # 원인이 성립한 뒤 8시간에 발화
    warn_before_s: 7200     # 발화 2시간 전부터 예고 구간
    emits: [PLC+1|space:bug@>=many]
```

- 발화 시점에 `on` 조건이 **거짓이면 취소**한다. 방치 중에는 유지되어 발화하고, 그 사이 치우면 예약은 사라진다.
- **원인당 예약은 하나**다. 같은 원인이 여러 번 쌓여도 예약이 중복되지 않는다. 이것이 예약의 유일한 리미트다.
- 예약의 생애는 사건 기록으로 남는다: `delay_scheduled` → `delay_warned` → `delay_fired` 또는 `delay_cancelled`.

## 10. 저항 (단계별 행동 비용)

행동의 비용을 단계 키 조건의 표로 정한다. 조건 표 방식은 상태 의미와 같다.

```yaml
actions:
  wipe:
    cost:
      - when: body:rot@<wilted   # 젖음·마름 단계
        items: { 물티슈: 1 }
        time: 1
      - when: body:rot@>=spoiled # 고착 단계
        items: { 세제: 1 }
        time: 3
```

- 비용은 기존 물품과 시간 자원에서 빠진다. 새 결과를 만들지 않는다.
- 저항은 상한이 아니다. 방치하면 더 나빠질 수는 있어도(단계 사다리 끝까지), 비용이 늘어나는 것은 저항이다.

## 11. 예고 단계와 알아챔 (범위의 끝)

이 절이 지연 판정의 **범위 끝**이다. 확률, 자유 입력, 예고의 연출 세부는 다루지 않는다.

- **예고 구간**: 발화 전 `warn_before_s` 동안이다. 이 구간에 플레이어는 행동으로 원인을 바꿀 수 있다. 원인이 풀리면 발화 시점 판정에서 취소된다.
- **하루씨의 알아챔**: 예고는 하루씨가 **지각 임계를 넘을 때만** 알아챈다 (인지 단계 모름 → 알아챔). 알아채면 자율 행동 후보에 들어간다 (예: 닦기, 버리기).
- **플레이어가 먼저 아는 경우**: 하루씨가 알아채지 못해도 플레이어에게는 예고가 보인다. 극적 아이러니의 자리다 (인물-명세 13).
- 알아챔 임계는 감각 민감도(`senses.*`, 인물 파라메터)에서 온다. 임계 값은 임시값이다.

## 12. 구현 목록 (다음 작업, 이 문서 범위 밖)

1. 수지 검사: 접촉 전달의 양 보존 시험.
2. 규칙에 `delay_s`, `warn_before_s` 필드 추가 (db 형식, 관문 검사, 발화 시 재판정).
3. 행동의 `cost` 표 (단계 키 조건, 물품·시간 차감).
4. 사건 유형 `delay_scheduled`, `delay_warned`, `delay_fired`, `delay_cancelled` 를 사전에 등록.
5. 예약 중복 방지 시험 (원인당 하나).
6. 알아챔 임계 시험 (민감도 낮으면 플레이어만 보는지).

## 13. 운명 엔진과의 대조 (make-bio-database `docs/design/cell-fate-engine.md` 기준)

읽은 범위: 설계 문서만. 엔진 코드와 시험 코드는 읽지 않았다. 아래는 문서에 적힌 방식과 우리 설계의 비교다.

### 13-1. 구조가 맞는 부분

| 운명 엔진 | 우리 설계 | 판단 |
|---|---|---|
| 데이터가 상태·신호·규칙을 정하고, 엔진은 이름을 모른다 | 같은 원칙 (CLAUDE: 엔진은 이름을 모른다) | 맞음 |
| 보존은 구조로 보장 (`N = N₀ + S·ξ`), 감사는 확인용 | 보존 강제 (결정 1) | 맞음. 방식을 가져오면 된다 |
| 결정론 실행 위에 확률 층을 시드와 함께 얹음 | 난수는 이벤트 발생에만 | 맞음 |
| 신호를 0으로 두고 되돌아가는지 본다 (신호 철회 시험) | 자국이 되돌려지는지, 행동만 지우는지 | 자국 정의에 바로 쓸 수 있다 |
| 가정 상수는 `hypothetical`, 결과는 예측이 아니라 "가능한 것" | 임시값 `tuned:false`, 정답 아님 | 맞음 |
| 사후 분석의 원인 분류 | 하루 원인 분류 (에너지·동기·방해·대안·도구) | 이미 가져옴 |

### 13-2. 바꿔야 할 부분 (세 가지)

**(가) 저장은 양, 단계는 파생.** 운명 엔진은 반응 진행량 ξ를 저장하고 N = N₀ + S·ξ로 양을 만든 뒤, 단계(상태)를 농도에서 계산한다. 우리는 지금 단계 정수를 저장한다. 이 차이가 병목 2번(양 저장)의 답이다. 보존도 같은 식에서 저절로 나온다.
- 문제: 우리 규칙 "수량은 정수"와 충돌한다. 운명 엔진은 부동소수에 보정 합(TwoSum)을 쓴다.
- 권장: 양을 **정수 단위**로 저장한다 (예: 1/1000 단위). 그러면 보존이 정확히 성립하고, 부동소수 허용 오차가 필요 없다.

**(나) 누적은 연산자 분리를 쓰지 않는다.** 운명 엔진은 처음에 "빠른 층은 음해법, 느린 층은 고정 인자 지수 갱신"으로 풀었다가, 1차 오차 6e-4~1e-2 때문에 버렸다. 우리 설계의 "구간 상수 속도 + 경계마다 재계산"이 같은 방식이다.
- 권장: 구간 상수는 **작은 간격의 참조 해와 비교하는 시험을 필수**로 둔다. 오차 허용을 넘으면 경계를 더 잘게 나눈다.

**(다) 조절은 곱으로 통일한다.** 운명 엔진은 조절자가 규칙 속도를 곱한다. 우리 속도 법칙(축과-층위 8)은 가속을 `1 + Σ`로 **더한다.** 같은 문서 안에서 "조절자는 중립값 1로 곱한다"는 규칙과도 어긋난다.
- 권장: **곱으로 통일한다.** 중립값 1, 여러 조절자는 곱. 특성 보정(물먹음 등)도 같은 곱으로 들어간다.

### 13-3. 빠져 있던 것

- **지연 예약은 운명 엔진에 없다.** 운명 엔진은 연속 흐름과 사건 시각의 근 찾기만 있다. 우리 지연(예약, 발화 시 재판정, 취소)은 **연속 흐름 + 사건 큐**의 하이브리드가 필요하다. 흐름은 적분하고, 사건은 큐에서 꺼낸다.
- **DB-개념-이식 7장의 "가져오지 않는 것"을 다시 봐야 한다.** 거기 적은 "대사 원장과 부분 구조 수지, 질량 감사"는 화학 부분이다. 하지만 보존 강제의 핵심 방식이므로, 화학 부분만 빼고 **보존 구조는 가져와야 한다.** 이 부분의 설명을 고치는 것이 맞다.
- **고정 상태의 측정**: 자국이 "행동으로만 지워진다"는 주장을 되돌림 시험으로 재면 된다. 신호(세제 닦기)를 0으로 두고 일정 시간 뒤에도 자국이 남는지 본다.

### 13-4. 결론

구조는 잘 맞는다. 보존, 데이터 주도, 결정론과 확률의 분리, 되돌림 시험이 그대로 쓰인다. 다만 **저장 방식(양 저장), 누적 검증(참조 해), 조절 방식(곱)** 세 가지는 운명 엔진의 방식으로 바꿔야 한다. 지연 예약은 운명 엔진에 없으므로 우리가 따로 설계해야 한다.
