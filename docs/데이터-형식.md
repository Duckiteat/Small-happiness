# 데이터 입력 형식 (고정안)

작성일 2026-11-05 · 상태: **고정안 (작가 확인 대기 3건, 9장)**. 이 문서는 작가가 데이터를 쓰는 형식과, 그것이 기존 패치 파이프라인으로 들어가는 길을 정한다. 필드 설계의 근거는 `데이터-입력-설계-보고서.md`, `축-상호작용-설계.md`다.

---

## 1. 원칙

1. **작가는 원본 파일을 쓴다. `data/db.json`과 패치 JSON은 직접 고치지 않는다.** 원본 → 컴파일 → 패치 → 관문 순서로만 들어간다 (CLAUDE 데이터 규칙).
2. **한 파일 = 한 묶음.** 같은 종류, 같은 장소 또는 같은 맥락을 한 파일에 둔다. 파일 이름은 사람이 찾기 쉽게 짓는다.
3. **번호는 쓰지 않는다 (새 항목).** 새 항목은 임시 번호(`OBJ+1`)를 쓴다. 기존 항목은 정식 번호나 이름으로 가리킨다.
4. **단어는 사전에서만 고른다.** 특징, 감각, 행동, 단계 키, 종결 단계는 모두 사전 항목이어야 한다. 사전에 없으면 컴파일이 거부한다.
5. **펼치기는 컴파일이 한다.** `is_a`, `traits`, 차이만 적은 개별 물건은 원본에 그대로 두고, 컴파일 결과에서 펼친다. 실행 중에는 펼친 값만 읽는다.
6. **임시값은 표시한다.** 확인되지 않은 수치는 `tuned: false`, 가정은 `hypothetical: true`로 적는다.

## 2. 파일 머리 (모든 파일 공통)

```yaml
why: 냉장고와 사과 시나리오 첫 묶음 (임시값 포함)   # 필수. 패치 why 로 들어간다
file_kind: objects                                  # objects | places | materials | traits | characters | actions | rules
defs:
  - ...                                             # 항목 목록
```

- `why`가 없으면 컴파일이 거부한다 (기존 관문 규칙).
- `file_kind`는 항목의 종류를 제한한다. 한 파일에 여러 종류를 섞지 않는다.

## 3. 항목 종류별 필드

각 항목의 `status` 열: **구현** = 지금 관문이 받는다, **명세** = 이 문서가 정하고 db·관문 작업이 남았다.

### 3-1. 물건 분류 (`kind: class`) — 명세

| 필드 | 뜻 | 상태 |
|---|---|---|
| `id` | 임시 번호 `KND+1` (새 접두) | 명세 |
| `names`, `aliases`, `desc` | 이름과 설명 | 구현 (OBJ 와 같은 형태) |
| `material` | 기본 재질 (재질 항목 번호 또는 이름) | 명세 |
| `offers` | 제공 행동 목록 (사전 행동 키) | 명세 |
| `parts` | 부위 목록: `{ 부위: { material, features } }` | 구현 (`slots`) + 명세 (`material`) |

### 3-2. 개별 물건 (`kind: object`) — 구현·명세

```yaml
- id: OBJ+1
  names: { ko: 주방 냉장고 }
  is_a: KND000012              # 명세: 분류를 펼친다
  mobility: fixed              # 구현 (사전 mobility)
  override:                    # 명세: 분류와 다른 것만
    parts:
      door: { material: 스테인리스 }
  slots:                       # 구현 (기존 형식 그대로)
    body: { features: [rot, smell] }
  rules:
    spoil:                     # 구현 (규칙 형식은 3-6)
      label: 음식이 상하면 냄새가 뚜렷해진다
      on:   [OBJ+1|body:rot@>=spoiled]
      emits: [OBJ+1|body:smell@>=distinct]
```

- `is_a` 와 `override` 는 컴파일이 펼친다. 펼친 결과는 기존 `slots`·`rules` 형식이다.
- `slots` 의 특징은 사전 특징이다. 단계 조건은 사전 `levels` 의 키로 쓴다 (`@>=spoiled`). 잠긴 칸(`locked`)은 쓰면 거부된다.

### 3-3. 재질 (`kind: material`) — 명세

```yaml
- id: MAT+1
  names: { ko: 합판 }
  is_a: MAT000001              # 나무 (필요할 때만)
  traits:                      # 특성 부착: 사전 특성 이름 + 세기
    - { trait: 얼룩, level: 잘탐 }
    - { trait: 물먹음, level: 3, tuned: false }
    - { trait: 곰팡이민감, level: 2, tuned: false }
    - { trait: 고유감각, level: 드르륵스르륵 }
```

- 특성의 **뜻과 보정표는 사전**에 있다 (`trait` 항목, 9장 결정 2). 재질은 세기만 고른다.
- 세기 숫자의 뜻은 작가가 정하지 않았다 (9장 결정 3에서 정한다). 지금은 `level` 로 적고 컴파일은 사전 `trait` 의 허용 값과 대조한다.

### 3-4. 장소 (`kind: place`) — 구현·명세

```yaml
- id: PLC+1
  names: { ko: 주방 }
  slots: { space: { features: [smell, bug] } }      # 구현
  environment:                                       # 명세 (세계-설정 3)
    weather_effect: 거실쪽 약함   # 확인: 값은 사전 항목 키로 바꾼다
    temp_swing: 낮음
    ventilation: 어려움
    humidity: 보통
  passages:                                          # 명세: 통로 (그래프 간선)
    - { to: PLC+2, kind: open, transfer_by_medium: { air: 100 } }
```

### 3-5. 인물 (`kind: character`) — 명세

```yaml
- id: CHR+1
  names: { ko: 하루씨 }
  senses:                      # 사전 감각 키 → 민감도 1~5 (정수)
    smell: 4
    touch: 2
    proprioception: 3
  taste_bias: { 단맛: 0 }
  params:                      # 인물 파라메터 (값에 tuned 표시)
    buffer_gain: { value: 200, unit_pct100: true, tuned: false }   # 0.2 = 20 % 를 ×100 정수
    release_threshold: { value: 800, unit_pct100: true, tuned: false }
  habits: [HAB000001]          # 습관 정의 번호
```

- 인물의 파라메터 키는 사전 `param` 항목만 쓴다. 이벤트는 이름이 아니라 키로 읽는다 (인물 1명 규칙, 축과-층위 7).

### 3-6. 규칙 (`rules` 블록) — 구현·명세

```yaml
rules:
  bugs_swarm_after_rot:
    label: 상한 음식을 오래 두면 다음 날 벌레가 들끓는다
    on: [OBJ+1|body:rot@>=spoiled]
    emits: [PLC+1|space:bug@>=many]
    delay_s: 28800               # 명세: 원인 성립 후 8시간에 발화 (발화 시 재판정)
    warn_before_s: 7200          # 명세: 발화 2시간 전 예고 구간
```

- `label`, `on`, `emits` 는 구현됨. `delay_s`, `warn_before_s` 는 명세다 (축-상호작용 9).
- 같은 원인(규칙 + 주어)의 예약은 하나만 둔다. 이것은 엔진 규칙이며 데이터에 쓰지 않는다.

### 3-7. 행동 (`kind: action`) — 명세

```yaml
- id: ACT+1
  verb: wipe                     # 사전 행동 키 (닦기)
  names: { ko: 닦기 }
  needs: [{ item: ITM+1, amount: 1 }]   # 명세: 물티슈, 1장 (기본)
  cost:                          # 명세: 단계 키 조건 표 (축-상호작용 10)
    - { when: body:rot@<wilted,  items: { ITM+1: 1 }, time_s: 60 }
    - { when: body:rot@>=spoiled, items: { ITM+2: 1 }, time_s: 180 }   # 세제
  effect:                        # 명세: 효과 요청 (결과는 엔진이 정한다)
    - { target: body, feature: rot, set: lowered_residue }   # 확인: 효과 어휘 9장 결정 4
```

- 효과는 "무엇을 하라"만 적는다. 결과 값을 직접 쓰지 않는다 (CLAUDE: 결과를 직접 정하지 않고 효과 요청을 거친다).

### 3-8. 특성 (`kind: trait`, 사전 항목) — 명세

특성은 사전에 둔다. 재질·물건에 붙는 이름과 보정표의 뜻을 한 곳에 정한다.

```yaml
# data/vocab 의 trait 분류
- key: 곰팡이민감
  ko: 곰팡이 민감
  attrs:
    applies_to: [body]                 # 붙을 수 있는 부위
    feature: rot                       # 이 특성이 만지는 특징
    modifiers:                         # 단계 키 조건 → 가속 배율 (×100)
      - { when: wet@>=wet,    accel100: 150 }
      - { when: wet@>=soaked, accel100: 200 }
```

- `when` 은 사전 특징 `wet` 의 단계 키 조건이다 (구현된 조건 문법과 같음).
- 보정표는 위에서부터 처음 맞는 값을 쓴다 (`meanings` 와 같은 규칙).

### 3-9. 감각·내구·종결 (사전 항목) — 구현

- 감각: `sense` 분류 (고유감각 포함). 구현.
- 내구 배율: `durability` 분류 (취약 50 · 평균 100 · 강점 150 · 큰 강점 200). 구현.
- 종결: `terminal` 분류 (소멸 · 고정). 구현.

## 4. 단위와 숫자 규칙

| 종류 | 표기 | 예 |
|---|---|---|
| 시간 | 정수, 초, 이름 끝 `_s` | `delay_s: 28800` |
| 배율·비율 | 정수, ×100, 이름 끝 `100` 또는 `_pct100` | `accel100: 150` |
| 양 | 정수, 1/1000 단위, 이름 끝 `_milli` | `amount_milli: 1000` (= 1 단위) |
| 세기·민감도 | 정수 (세기 숫자의 뜻은 9장) | `level: 3` |
| 임시값 | `tuned: false` 필수 | 물먹음 3 |
| 가정 | `hypothetical: true` | 시험용 상수 |

- 부동소수는 원본에 쓰지 않는다. 소수가 필요하면 위 표의 정수로 바꾼다.

## 5. 컴파일 파이프라인

```
원본 YAML (data/src/*.yaml)
  → ① 형식 검사   파일 머리, 종류별 필드, 단위 표기, 임시 번호 형식
  → ② 사전 대조   모든 키·단어·단계 키가 사전에 있는가, 잠긴 칸을 쓰지 않았는가
  → ③ 펼치기      is_a · override · traits(보정표 부착) 를 펼친다
  → ④ 패치 생성   기존 defs 형식의 패치 JSON (why 포함)
  → ⑤ 기존 관문   validate → merge → gate (이 단계부터는 지금 파이프라인 그대로)
```

- ①·②·③·④ 는 새 코드다. ⑤ 는 있다.
- 컴파일은 원본을 고치지 않는다. 출력은 패치 파일이고, 패치만 관문을 거쳐 `data/db.json`으로 들어간다.
- 명세 필드(3장의 "명세")는 ①에서 형식만 검사하고, ③·⑤에서 들어갈 자리가 생길 때 켠다. 그 전에는 컴파일이 "아직 받지 않는 필드" 오류로 거부한다.

## 6. 형식 버전

- 이 문서는 `format_version: 1` 이다. 원본 파일 머리에 `format_version: 1` 을 적는다 (생략 시 거부).
- 필드를 바꾸면 버전을 올리고, 옛 원본은 변환 스크립트(`migrations/`)로 옮긴다 (CLAUDE 형식 규칙).

## 7. 파일 배치

```
data/src/
  objects/      물건과 분류
  materials/    재질
  places/       장소
  characters/   인물
  actions/      행동
  rules/        규칙 묶음 (필요 시)
data/vocab/     사전 (특성·감각·종결·내구 포함)
```

## 9. 작가 확인 3건 (고정안의 기본값으로 진행하고, 바꾸면 알려 달라)

1. **원본 형식 = YAML.** 기본값. 필요하면 `yaml` 패키지를 추가한다 (의존성 추가이므로 허락 필요). 허락이 없으면 같은 구조를 JSON으로 쓴다.
2. **특성의 뜻과 보정표는 사전에 둔다.** 재질은 세기만 고른다 (3-3, 3-8). 기본값.
3. **세기 숫자(물먹음 3, 곰팡이 2)의 뜻.** 기본값: 정수 세기 1~5로 두고, 특성 보정표가 그 세기에서 배율을 계산한다. 아직 배율 함수는 정하지 않았다 (나중 결정).

**아직 정하지 않은 항목 (이 고정안 밖):** 효과 어휘(행동의 `effect` 키), 이벤트 정의(EVT)와 선택지 형식, 자원 종류(ITM)의 수량 규칙. 이것들은 해당 작업 전에 같은 방식으로 고정한다.
