# 데이터 입력 형식 (4층 고정안)

작성일 2026-11-05 · 상태: **고정안**. 확정/잠정 표시는 0장의 표기를 따른다. 필드 설계의 근거는 `데이터-입력-설계-보고서.md`, `축-상호작용-설계.md`다.

**표기** (필드와 항목의 상태)
- **구현** = 지금 `compile`과 관문이 받는다.
- **확정** = 형식을 정했고 구현만 남았다.
- **잠정** = 엔진 스파이크(양 저장, 누적 검증) 결과에 따라 바뀔 수 있다. 소비하는 코드가 없으므로 지금은 형식만 정한다.

---

## 0. 층 구조

데이터 필드는 4개의 층과 하나의 문장 트랙으로 나눈다. 이것은 **작성(데이터) 층**이며, 실행 층(`축과-층위.md`의 아홉 층)과는 다르다.

| 층 | 이름 | 한 줄 정의 | 읽을 수 있는 아래 층 |
|---|---|---|---|
| **L0** | 사전 | 이름이 붙은 **재사용 조각**을 정한다 (단어, 특성 등급, 재질) | 없음 |
| **L1** | 근본 속성 | 장소와 인물 같은 **자리의 사실**을 정한다 (환경, 통로, 감각, 파라메터) | L0 |
| **L2** | 조합과 변형 | L1을 골라 **개체를 만든다** (분류, 개별 물건, 부위) | L0, L1 |
| **L3** | 상호작용 | 개체들이 **시간과 접촉으로 어떻게 변하는가**를 정한다 | L0, L1, L2 |
| 트랙 | 문장 | 대사, 장면, 선택지 문구 | L3의 상태·사건 |

### 참조 방향 규칙 (컴파일러가 검사한다)

1. **위 층은 아래 층을 가리킬 수 있고, 아래 층은 위 층을 가리킬 수 없다.** 재질(L1)이 규칙(L3)을 가리키면 거부한다.
2. 같은 층 안의 참조는 허용한다 (재질의 `is_a` 등). 순환은 거부한다.
3. 문장 트랙은 L3만 읽는다. L0~L2를 직접 가리키지 않는다.

상태: **확정** (검사는 구현 대기).

## 1. 공통 원칙

1. **작가는 원본 파일을 쓴다.** `data/db.json`과 패치 JSON은 직접 고치지 않는다 (CLAUDE 데이터 규칙).
2. **한 파일 = 한 묶음.** 같은 층, 같은 종류, 같은 장소 또는 맥락을 한 파일에 둔다.
3. **새 항목은 임시 번호를 쓴다** (`OBJ+1`). 기존 항목은 정식 번호나 이름으로 가리킨다.
4. **단어는 사전에서만 고른다.** 사전에 없는 키는 컴파일이 거부한다.
5. **펼치기는 컴파일이 한다.** 실행 중에는 펼친 값만 읽는다.
6. **임시값은 표시한다.** `tuned: false`, 가정은 `hypothetical: true`.

### 파일 머리 (모든 원본 파일)

```json
{
  "format_version": 1,
  "file_kind": "objects",
  "why": "필수. 패치 why 로 들어간다",
  "defs": []
}
```

### 단위와 숫자

| 종류 | 표기 | 예 |
|---|---|---|
| 시간 | 정수, 초, 이름 끝 `_s` | `delay_s: 28800` |
| 배율·비율 | 정수, ×100, 이름 끝 `100` | `accel100: 150` |
| 양 | 정수, 1/1000 단위, 이름 끝 `_milli` | `amount_milli: 1000` |
| 세기·민감도 | 정수 | `level: 3` |
| 임시값 | `tuned: false` 필수 | |
| 가정 | `hypothetical: true` | |

부동소수는 원본에 쓰지 않는다.

## 2. L0 어휘 (사전)

사전은 `data/vocab/`의 분류별 JSON이다. 항목의 뜻과 속성이 이 층에서 정해진다.

| 분류 | 정하는 것 | 상태 |
|---|---|---|
| `feature` | 특징과 단계 사다리 (0~5, 칸마다 키·이름, 2·4는 `locked`) | 구현 |
| `sense` | 감각 (시각·청각·후각·촉각·미각·고유감각) | 구현 |
| `terminal` | 종결 단계 (소멸·고정). 조건은 `=`만 | 구현 |
| `durability` | 내구 배율 (취약 50 · 평균 100 · 강점 150 · 큰 강점 200) | 구현 |
| `mobility`, `contact`, `medium`, `spreader`, `action` | 기존 분류 | 구현 |
| `trait` | 특성 **개념** (이름, 붙을 부위, 만지는 특징). 등급 숫자는 갖지 않는다 | 확정 |
| `material` | **재질**. 이름과 `trait_grade` 키 목록. 숫자를 들고 있지 않다 | 확정 |
| `trait_grade` | 특성의 **등급 항목** `<특성>_<1~5>`. 각 항목이 자기 보정값을 이미 가지고 있다. 재질은 이 항목을 떼어 쓴다 | 확정 |
| `param` | 인물 파라메터 키 (여유·긴장 등) | 확정 |

등급 항목은 사전에 **완성된 조각으로** 둔다. 값은 항목이 직접 가진다. 숫자에서 배율을 계산하는 함수는 없다.

```json
{
  "category": "trait_grade",
  "entries": [
    { "key": "water_absorb_3", "ko": "물먹음 3",
      "attrs": { "trait": "water_absorb", "grade": 3, "wet_gain100": 150 } },
    { "key": "water_absorb_5", "ko": "물먹음 5",
      "attrs": { "trait": "water_absorb", "grade": 5, "wet_gain100": 250 } },
    { "key": "mold_prone_2", "ko": "곰팡이 민감 2",
      "attrs": { "trait": "mold_prone", "grade": 2,
        "modifiers": [
          { "when": "wet@>=wet",    "accel100": 150 },
          { "when": "wet@>=soaked", "accel100": 200 }
        ] } }
  ]
}
```

- **키 규칙**: `<특성 키>_<등급 숫자>` (영소문자·밑줄·숫자). 같은 특성의 등급은 1~5 중 쓰는 칸만 둔다.
- `when`은 단계 키 조건이다. `modifiers`는 위에서부터 처음 맞는 값을 쓴다 (심한 것을 위에).
- **작성 편의**: 같은 특성의 등급을 한 번에 적는 선언(`{ trait, grades: { "1": {...}, "2": {...} } }`)을 허용한다. 로드할 때 위와 같은 개별 항목으로 펼쳐지므로, 컴파일 이후에는 차이가 없다.
- 새 등급은 항목을 **더하는** 것으로 끝난다. 기존 항목의 값은 바꾸지 않는다 (뜻 불변, 축과-층위 6).

재질도 사전 항목이다. 등급 항목의 키를 모은 조각이다.

```json
{
  "category": "material",
  "entries": [
    { "key": "plywood", "ko": "합판",
      "attrs": { "traits": ["stain_prone_3", "water_absorb_3", "mold_prone_2", "proprio_rattle_1"] } },
    { "key": "stainless", "ko": "스테인리스",
      "attrs": { "traits": ["water_absorb_1", "mold_prone_1"] } }
  ]
}
```

- 모든 항목은 `trait_grade` 사전 키여야 한다. **한 특성당 등급은 하나**다 (`water_absorb_3`과 `water_absorb_5`를 함께 쓰면 거부).
- 재질은 상속하지 않는다. 특성 목록을 직접 적는다. 재질을 바꾸려면 키를 바꿔 끼운다.
- 물건과 분류는 재질을 **사전 키**(`plywood`)로 가리킨다. 재질 번호(`MAT`)는 만들지 않는다.
- 사전에 둔 이유: 재질은 여러 물건이 떼어 쓰는 조각이고, 번호가 아니라 이름으로 가리키는 것이 맞다.
- 성능: 컴파일이 재질을 한 번 펼치고, 실행 중에는 펼친 값만 읽는다. 사전에 두어도 속도 차이가 없다 (측정: 재질 1,000개에서 로드 약 13 ms, 조회는 항목 수와 무관).

## 3. L1 근본 속성

"이것이 무엇인가". 상호작용을 일으키지 않고 사실만 적는다.

### 3-1. 재질은 L0로 옮겼다

재질은 사전 `material` 분류에 있다 (2장). L1에는 재질 파일이 없다. 장소와 인물만 L1에 둔다.

### 3-2. 장소 환경 (`file_kind: places`) — 확정

```json
{
  "id": "PLC+1",
  "names": { "ko": "주방" },
  "environment": { "weather_effect": "low", "temp_swing": "low", "ventilation": "hard", "humidity": "mid" },
  "passages": [{ "to": "PLC+2", "kind": "open", "medium_pass": { "air": 100 }, "tuned": false }]
}
```

- 구현 (2026-11-07): `environment`는 사전 `env_trait` → `env_level`(매우 낮음·낮음·보통·높음). `passages`의 `kind`는 `edge_kind`, `medium_pass`는 `medium` → 0~1000, **`tuned`가 필수**(투과율은 실측이 없다). 적지 않은 매질은 0(지나가지 못함). 통로는 방향이 없고 한 쌍을 한쪽에만 적는다. 대상은 번호나 이름.

값은 사전 항목 키다. 장소의 `slots`와 `rules`는 L2/L3에 속한다 (4장, 5장).

### 3-3. 인물 (`file_kind: characters`) — 확정

```json
{
  "id": "CHR+1",
  "names": { "ko": "하루씨" },
  "senses": { "smell": 4, "touch": 2, "proprioception": 3 },
  "params": { "buffer_gain": { "value": 20, "tuned": false } },
  "habits": ["HAB000001"]
}
```

- `senses`는 감각 민감도(1~5). 지각 임계가 이 값을 읽는다 (L3).
- **구현과 다름 (2026-11-06, 작가 확인 대기)**: 구현은 민감도 대신 **알아채는 사다리 칸**을 직접 받는다 — `"senses": { "smell": { "notice": 1, "tuned": false } }` (낮을수록 예민). 민감도 1~5를 칸으로 바꾸는 식을 지어내지 않으려는 것이다. 민감도 형식으로 갈지, 칸 형식으로 고정할지 정해야 한다 (`결정-기록.md` 4장 "지각과 행동").
- 제공 행동(`offers`)은 구현에서 물건·장소 정의에 붙는다: `{ verb, needs: [{ aware, at_least }], effect: [...], reveals?, minutes, tuned }` (상호작용-명세 3장). 4-1의 분류(KND) `offers` 목록과의 관계는 분류 구현 때 정한다.
- `params`의 키는 `param` 사전 항목이다. 값은 정수(×100).

## 4. L2 조합과 변형

L1을 골라 개체를 만든다.

### 4-1. 분류 (`file_kind: classes`) — 확정

> **첫 구현 (2026-11-06)**: 별도의 `KND` 번호 대신 **물건 정의의 `is_a`(한 단계)**로 시작했다. 종류(예: 음식 `OBJ000001`)에 규칙·제공 행동을 한 번 쓰면 `is_a`로 속한 물건이 실행 중에 물려받고, 같은 키를 가지면 덮어쓴다 (`src/core/kinds.ts`). 원본 컴파일러는 부위·상태 의미만 펼치고 규칙·행동은 복사하지 않는다. 규칙에는 `on_all`(종류 전부가 맞아야 함), 제공 행동에는 `when`(행동할 수 있는 상태)을 더했다. 실제 내용은 `content/src/`에 원본으로 쓰고 `compile → validate → merge`로 넣는다. `KND`로 옮길지는 분류가 더 필요해질 때 정한다.

```json
{
  "id": "KND+1",
  "names": { "ko": "음식" },
  "slots": { "body": { "features": ["rot", "smell"] } },
  "material": "plywood",
  "offers": ["eat", "throw"]
}
```

### 4-2. 개별 물건 (`file_kind: objects`) — 구현·확정

```json
{
  "id": "OBJ+2",
  "is_a": "OBJ+1",
  "names": { "ko": "사과" },
  "override": { "mobility": "가변" }
}
```

- `is_a`와 `override`는 같은 파일 안에서 한 단계만 펼친다 (**구현**). 분류(`KND`)를 가리키는 `is_a`는 **확정, 구현 대기**.
- `override`로 바꿀 수 있는 필드: `mobility`, `slots`, `meanings`, `rules` (구현). `parts`, `material`은 확정.
- 개별 물건은 **규칙을 직접 갖지 않는다** (아래 5장의 작성 규칙 참조). 지금은 db 형식 때문에 `rules`를 받지만, 이 필드는 L3 파일에서 붙이는 방향으로 옮긴다 (잠정).

## 5. L3 상호작용

가장 큰 층이다. 개체 하나하나가 아니라 **상태(특징)와 패턴**을 단위로 쓴다. 세 개의 파일 종류로 나눈다.

### 5-1. 규모가 커지는 이유와 관리 방법

- L3는 특징 수 × 맥락 수 × 행동 수에 비례해서 커진다. 개체 수(L2)와 별개다.
- **규칙은 개체가 아니라 분류, 특성, 특징에 대해 쓴다.** "OBJ000001 사과의 상함 규칙"이 아니라 "음식 분류의 상함 규칙"이다. 그렇지 않으면 물건이 늘 때마다 규칙이 늘어난다.
- 세 종류로 나눠 파일을 작게 유지한다 (5-2~5-4). 완전성 검사(5-5)가 빠진 곳을 알려 준다.

### 5-2. 진행 (`file_kind: progress`) — **잠정**

**모든 특징은 자기 진행 법칙을 가진다.** 시간이 지나면서 상태가 얼마나 쌓이는지를 정한다 (이것이 "모든 상태에 대한 누적"이다). 특징당 파일 하나.

```json
{
  "feature": "rot",
  "base_s": 86400,
  "inputs": {
    "temp": [{ "bin": "cold", "coef100": 10 }, { "bin": "room", "coef100": 100 }],
    "humidity": [{ "bin": "dry", "coef100": 80 }, { "bin": "wet", "coef100": 150 }],
    "process": [{ "bin": "whole", "coef100": 100 }, { "bin": "cut", "coef100": 300 }]
  },
  "floor_s": 3600,
  "accel_cap100": 300,
  "stage_edges_milli": [0, 200, 500, 800, 950, 1000]
}
```

- `base_s`: 중립 입력일 때 한 단계가 오르는 시간. `inputs`: 구간 키 → ×100 계수 표 (축마다 따로).
- `floor_s`, `accel_cap100`: 최단 시간과 가속 상한. 방치해도 한계가 있도록 한다.
- `stage_edges_milli`: 양에서 단계를 파생하는 경계 (양 저장 방식 확정 전이라 **잠정**).
- 조절자(특성)는 이 법칙의 속도를 **곱한다** (곱 통일은 권장안, 확정 전).
- 서로 다른 특징은 서로 다른 진행 법칙을 가진다 (신선도와 곰팡이는 다른 축).

### 5-3. 결합 (`file_kind: couplings`) — 구현·확정·잠정

특징과 개체 사이의 연결을 적는다.

```json
{
  "owner": "KND+1",
  "rules": {
    "spoil": {
      "label": "상하면 냄새가 뚜렷해진다",
      "on": ["KND+1|body:rot@>=spoiled"],
      "emits": ["KND+1|body:smell@>=distinct"],
      "delay_s": 28800,
      "warn_before_s": 7200
    }
  }
}
```

| 필드 | 상태 |
|---|---|
| `label`, `on`, `emits` | 구현 (지금은 개체 정의 안의 `rules`) |
| `owner`로 규칙을 L2 정의에 붙이기 | 확정, 구현 대기 (컴파일이 패치의 `rules`로 펼친다) |
| `delay_s` (+ 필수 `tuned`) | 구현 (2026-11-06, 60의 배수, `src/core/causal.ts`) |
| 진행 법칙 (`progress`: slot·base_s·inputs·edges·tuned·source) | 구현 1차 (2026-11-06, 물건 정의의 필드, `src/core/progress.ts`, `음식-변화-모델.md` 4·5장). 5-2의 `floor_s`·`accel_cap100`은 아직 |
| `warn_before_s` | 확정, 구현 대기 |
| 접촉 전달 (면, 전달률, 양) | 잠정 (양 저장 방식 확정 후) |
| 고정 → 소멸 전이 (행동·이벤트로) | 잠정 |

### 5-4. 행동·판정·이벤트 (`file_kind: actions`, `perception`, `events`) — **잠정**

```json
{
  "id": "ACT+1",
  "verb": "wipe",
  "cost": [
    { "when": "wet@<damp", "items": { "ITM+1": 1 }, "time_s": 60 },
    { "when": "wet@>=wet", "items": { "ITM+2": 1 }, "time_s": 180 }
  ],
  "effect": [{ "target": "body", "feature": "wet", "op": "lower" }]
}
```

- 행동은 효과 요청만 적는다. 결과 값은 엔진이 정한다 (CLAUDE).
- 지각(`perception`)은 민감도 임계로 알아챔을 정한다. 이벤트(`events`)는 포착 조건과 열림·닫힘 조건, 출처(시스템/주입)를 정한다.
- 이벤트의 선택지 문구와 대사는 이 층이 아니라 문장 트랙이다.

### 5-5. 완전성 검사 (컴파일러, 확정·구현 대기)

| 검사 | 내용 |
|---|---|
| 진행 완전성 | 사전의 모든 특징은 진행 법칙이 있거나 `static: true`로 선언해야 한다 |
| 행동 완전성 | 모든 행동 동사는 비용 표가 있거나 비용 없음을 선언한다 |
| 참조 방향 | 0장의 규칙 |
| 단계 조건 | 단계 키가 사전에 있고, 잠긴 칸이 아니다 (구현) |
| 규칙 참조 | `on`/`emits`가 가리키는 정의와 부위·특징이 있다 (구현, 병합 후 관문) |

## 6. 문장 트랙 — 확정 (형식만)

대사, 장면, 선택지는 L3의 이벤트·상태를 번호나 키로 가리킨다. 구체적인 조건이 많은 것이 먼저 뽑히고, 모든 장면에 일반 기본 문장이 있어야 한다 (축과-층위 2). 문장은 원문과 통제 태그로 저장한다. 필드의 세부는 이벤트 작업 전에 정한다.

---

## 7. 컴파일 파이프라인

```
원본 (data/src/)
  → ① 형식 검사   파일 머리, 종류별 필드, 단위 표기, 임시 번호        [구현: objects·places]
  → ② 사전 대조   키·단계 키가 사전에 있는가, 잠긴 칸을 쓰지 않았는가   [일부 구현]
  → ③ 펼치기      is_a · override · owner 규칙 붙이기 · 특성 부착        [is_a·override만 구현]
  → ④ 패치 생성   기존 defs 형식 (why 포함)                           [구현]
  → ⑤ 기존 관문   validate → merge → gate                            [구현]
```

- 컴파일은 원본을 고치지 않고, 파일도 쓰지 않는다. 명령 `compile`은 패치를 표준 출력으로 낸다.
- 아직 받지 않는 필드(5-2~5-4의 확정·잠정 필드와 L1·L2의 확정 필드)는 "아직 받지 않는 필드"로 거부한다.

## 11. 작가 확인 (기본값으로 진행하고 바꾸면 알려 달라)

1. **원본 형식 = JSON(지금), YAML은 `yaml` 패키지 추가 허락 후.**
2. **특성의 뜻과 보정표는 사전(L0)에 둔다.** 재질은 세기만 고른다.
3. ~~세기 숫자의 배율 함수~~ → **불필요.** 등급 항목이 값을 직접 가진다 (2장). 대신 각 등급 항목의 실제 값(배율, 가속 표)은 항목을 쓸 때 정한다.
4. **규칙은 개체 정의 안이 아니라 L3 파일에서 붙인다.** 지금 db 형식은 개체 안의 `rules`를 받으므로, 컴파일이 `owner` 규칙을 개체 정의의 `rules`로 펼친다.
5. **재질은 L0 사전 항목이다** (작가 확정). 재질 번호(`MAT`)는 만들지 않고 사전 키로 가리킨다.
