# 개발 계획서

**어떻게, 언제, 무엇으로 검증하는지**를 담는다. 무엇을·왜는 `기획보고서-v3.md`, 작업 항목 하나하나는 `구현-계획.md`에 있다. 작성일 2026-11-03. 상태: 초안.

---

## 1. 목적

1. 학교 과제로 **작동하는 수직 슬라이스**와 기획 보고서를 제출한다.
2. 이후 상업화로 확장할 수 있는 **구조**를 처음부터 세운다 (콘텐츠는 시스템에서 나오고, 데이터는 관문을 지난다).

### 4-1. 순서에 관한 판단

- **가장 큰 위험은 "읽을 만한가"** 이다. 지금까지는 설계가 구현을 앞섰고 플레이할 수 있는 것이 아직 없다. 그래서 M3~M4를 다 마치기 전에 **M2B로 줄글의 감을 먼저 본다**: 시스템을 하드코딩한 최소 진행으로도 문장과 링크가 살아 있는지는 확인할 수 있다.
- M3~M4는 이벤트 없이 시험한다. 이벤트는 M5에서 패치로 얹는다.
- 난수·시계·저장(6~8)은 M3에서 필요한 만큼 만든다.

### 4-2. 복잡도 관리 (2026-11-03 측정)

| 측정 | 값 |
|---|---|
| 구현된 코드 | 코어 2,054줄 + 어댑터 367줄 (시험 1,018줄) |
| 설계 문서 | 16개, 2,504줄 |
| 구현 계획 항목 | 42개 중 완료 5, 진행 3, 대기 34 |

- **구현은 작고 설계가 훨씬 크다.** 복잡도는 코드가 아니라 서로 맞물리는 **개념의 수**(정의 저장소, 번짐, 컨디션·모드, 밖의 하루, 자율 행동, 인지·습관·기억, 이벤트, 줄글·지도, 회상, 상태이상, 문장 엔진 …)에 있다.
- 완화 장치: 층 구조(각 층을 아래 층만으로 시험), 한 메커니즘의 반복(상태 키 + 패턴 + 규칙 + 관문), 관문과 시험.
- **최소 플레이어블 집합** (22A에 꼭 필요한 것): 정의 저장소(완료), 주방·냉장고·거실 3개 장소(5A 일부), 세계 상태(9), 변화 규칙 실행(10), 번짐 중 냄새·벌레(11 일부), 감각(후각·시각)과 인지 3단계(14·19 일부), 이벤트 포착기 하나(19A), 문장 조각 조회(20 일부), 지도 뷰 모델과 목록(22A 1단계), 상태이상 한 가지(감기, 14B 최소)로 "안 뜰 수도"를 시험.
- 이 집합에 **들어가지 않는 것**: 컨디션·모드·앙상블(15, 16, 16A, 16B), 조절 규칙 일반화(14A), 밖의 하루(17), 자율 행동(18), 습관, 기억, 정산·제한 요인(21, 21A), 난수·시계·저장(6~8), 거래 등.
- **개념 동결 제안**: 22A가 읽을 만하다고 확인되기 전에는 새 개념을 설계에 넣지 않고 6부(확장)에 적는다. 좋은 아이디어가 계속 나오는 것이 이 기획의 강점이지만, 구현 없이 개념만 늘면 길을 잃기 쉽다.

## 5. 검증 계획

### 5-1. 자동 (시험이 지킨다)

| 대상 | 검증 |
|---|---|
| 데이터 | 패치 관문: 사전·참조·부위·단계 범위·이름 충돌·번호 카운터·닫힘 조건 |
| 규칙 | 같은 입력 같은 결과, 변화 규칙이 난수에 접근하지 못함 |
| 보존 | 자원과 물건의 총량이 이유 없이 변하지 않음 |
| 앙상블 | 도움 없는 하루의 여유 평균 ≈ 0, 값 범위 유지, 모드 빈도 보고, 돕는 쪽 평균이 더 높음 |
| 비가역성 | 신호 철회 시험: 번짐 단계가 "싸게 되돌릴 수 있는 한계"를 넘는 지점 |
| 문서 | 자동 생성 부록이 최신 (`appendix --check`) |
| **꼼수 방지** | 거부 말뭉치와 바닥값, 금지 패턴 스캔, 재생(손 편집 탐지), 가드(규칙 변경 시 결정 기록), CI (`꼼수-방지.md`) |

### 5-2. 사람 (플레이테스트)

가설을 **실행 전에 적고 결과를 본 뒤 바꾸지 않는다.** 항목은 지금 정하고 수치는 등록 때 정한다.

1. 줄글을 눌러 이벤트를 **닫힘까지** 진행할 수 있다.
2. 방전한 날의 장면을 **죄책감 없이** 받아들인다.
3. 텍스트만으로 하루를 읽어도 **흥미가 유지**된다.
4. 하루를 마친 뒤 "오늘은 됐다"는 느낌이 남는다.
5. 하루씨에게 물건을 **사 주고 싶은** 마음이 든다 (개입 동기).

### 5-3. 한계

게임에는 현실이라는 정답지가 없다. 자동 검증은 **내부 일관성**만 보장하고, 재미와 읽을 만함은 플레이테스트로만 확인된다.

## 7. 자원과 방식

- 개발자 1명(작가), 아트는 전량 AI 생성, 코드는 AI의 도움을 받는다.
- **세션이 바뀌어도 방향을 잃지 않도록** 결정은 `결정-기록.md`에, 작업은 `구현-계획.md`에 남긴다.
- 모든 데이터 변경은 패치와 관문을 거치고, 설계 변경은 관련 명세와 결정 기록을 같은 커밋에서 고친다.
- 구현은 Sonnet급으로 충분하다고 보고, 되돌리기 어려운 설계 확정과 마일스톤별 교차 점검에만 더 강한 모델을 고려한다.

## 8. 일정과 미정 사항

- **마감일과 제출 형식(한글/워드/PDF)을 모른다.** 이 계획은 날짜가 아니라 순서와 완료 기준으로 쓰였다. 마감이 정해지면 M2B와 M6을 기준으로 역산한다.
- 소요 시간은 추정하지 않는다. M2에서 장소 하나를 완성하는 실제 시간을 재서 외삽한다.
- 미정: 하루씨의 직업·출퇴근, 욕실 문 위치, 가전, 쓰레기 배출, 링크 수명, 서술의 시점, 사전 초안 검토. (전체는 `결정-기록.md` 7장)
