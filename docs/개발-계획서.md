# 개발 계획서

**어떻게, 언제, 무엇으로 검증하는지**를 담는다. 무엇을·왜는 `기획보고서-v3.md`, 작업 항목 하나하나는 `구현-계획.md`에 있다. 작성일 2026-11-03 · **개정 1: 2026-11-10** · 상태: 초안 (개정 1의 순서와 일정은 **제안**, 작가 확인 대기는 10장).

**개정 1에서 바뀐 것**: 처음 계획(M0~M6) 뒤로 실제 작업은 `구현-계획.md`의 "지금 구간"(S1~S8, 개정 뒤 "지난 구간")으로 갔다. 그 결과를 4장에 반영하고, 남은 길을 다섯 단계(N1~N5)로 다시 짰다. 조기 줄글 프로토타입(M2B)은 회색 상자 한 바퀴(N2)로 바뀌었다. 3주 시한(`논의-메모.md` 6장)을 8장에 넣었다.

## 1. 목적

1. 3주 안에 **작동하는 시제품**을 만들어 학교 과제, **창업대회**, **AI 활용 수업 프로그램 대회**에 낸다 (`논의-메모.md` 1·6장).

### 4-3. 순서에 관한 판단

- **가장 큰 위험은 여전히 "읽을 만한가"다.** 엔진은 단단해졌지만 사람이 눌러 본 적이 없다 (`게임화-방향.md` 2장: "게임에 꽂을 손잡이가 아직 없다"). 그래서 N2를 N3보다 앞에 둔다.
- `기원-설계.md` 13-3은 감정을 먼저 고치자고 권한다. 두 권고를 이렇게 맞춘다: 화면 한 바퀴(N2)는 지금의 냉장고 장면으로 하고, 감정·기억(N3)은 그 화면 위에 두 번째 장면으로 얹는다. 화면이 먼저 있으면 N3의 결과를 바로 읽어 볼 수 있다.
- 임시값 맞추기(N4)는 화면이 생긴 뒤에 한다. 직접 해 봐야 맞출 수 있다.
- 범용화는 하지 않는다. 엔진 입구만 범용으로 짠다 (`게임화-방향.md` 9장).

## 5. 검증 계획

### 5-1. 자동 (시험이 지킨다)

| 대상 | 검증 | 상태 |
|---|---|---|
| 데이터 | 패치 관문: 사전·참조·부위·단계 범위·이름 충돌·번호 카운터·닫힘 조건·장소 연결성 | 있음 |
| 규칙 | 같은 입력 같은 결과, 변화 규칙이 난수에 접근하지 못함 (소스 검사) | 있음 |
| 사건 | **영수증 감사**: 사건이 근거(via)의 규칙·행동·진행·감각과 맞는지 정의에서 다시 계산, 원인 빈칸은 원천만 | 있음 (S1·S2) |
| 하루 | **하루 영수증**: 사건 사슬·하루 사슬 봉인, 고친 영수증 거부 | 있음 (21R) |
| 입구 | 나눠 진행해도, 저장했다 이어 가도 같은 하루 (바이트 일치) | 있음 (S8) |

| 비가역성 | 신호 철회 시험: 번짐 단계가 "싸게 되돌릴 수 있는 한계"를 넘는 지점 | 없음 (16B, 후속) |
| 문서 | 자동 생성 부록 최신 (`appendix:check`), 원인 빈칸 최신 (`gaps:check`), 보고서 목록 | 있음 |
| **꼼수 방지** | 거부 말뭉치와 바닥값, 금지 패턴 스캔, 재생(손 편집 탐지), 가드(규칙 변경 시 결정 기록), CI (`꼼수-방지.md`) | 있음 |

### 5-2. 사람 (플레이테스트)

가설을 **실행 전에 적고 결과를 본 뒤 바꾸지 않는다.** 항목은 지금 정하고 수치는 등록 때 정한다.

1. 줄글을 눌러 장면을 **닫힘까지** 진행할 수 있다.
2. 방전한 날의 장면을 **죄책감 없이** 받아들인다.
3. 텍스트만으로 하루를 읽어도 **흥미가 유지**된다.
4. 하루를 마친 뒤 "오늘은 됐다"는 느낌이 남는다.
5. 하루씨에게 물건을 **사 주고 싶은** 마음이 든다 (개입 동기).

N3 뒤에 더할 후보 (제안): 조언이 닿지 않은 순간을 **하루씨의 상태로 납득**한다.

### 5-3. 한계

게임에는 현실이라는 정답지가 없다. 자동 검증은 **내부 일관성**만 보장하고, 재미와 읽을 만함은 플레이테스트로만 확인된다. 감사는 엔진의 계산을 다시 하지만, 같은 사람이 같은 생각으로 짠 두 벌이라 **설계 자체의 잘못은 잡지 못한다** (`한계-등록부.md` LIM013~015).

| 감사 코드가 커짐 | 새 시스템을 N1~N5 경로로 제한 |
| 악순환(이월된 오염) | 증상 선행, 상한, 완충, 음성 되먹임 |
| AI 아트 정렬 | 구도 고정 후 오버레이 별도 생성, 코드보다 먼저 시험 (26) |
| 민감 주제(어머니의 죽음, 성숙한 주제)의 등급·배포 | 과거만 정함(`기원-설계.md`), 별도 팩, 옵트인, 등급 기준 사전 확인 |
| 모델·도구 의존 | 데이터와 설계는 문서에, 관문·감사·시험이 오류를 막음 |

## 7. 자원과 방식

- 개발자 1명(작가), 아트는 AI 생성 또는 미정(`게임화-방향.md` 11장), 코드는 AI의 도움을 받는다.
- **세션이 바뀌어도 방향을 잃지 않도록** 결정은 `결정-기록.md`, 작업은 `구현-계획.md`, 빠진 기능은 `한계-등록부.md`, 코드 변경은 `CHANGES.md`에 남긴다.
- 모든 데이터 변경은 패치와 관문을 거치고, 설계 변경은 관련 명세와 결정 기록을 같은 커밋에서 고친다.
- 되돌리기 어려운 설계 확정과 단계별 교차 점검에는 더 강한 모델을 고려한다.

## 8. 일정 (제안)

- 시한: **3주** (작가, 2026-11-05). 그날부터 세면 **11-26 무렵**이다. 시작일과 각 제출 마감은 **확인하지 못했다.**
- 남은 기간을 주 단위로 나눈 안 (마감이 정해지면 N5를 기준으로 거꾸로 다시 짠다):

## 9. 변경 관리

| 규칙 | 내용 |
|---|---|
| 결정 | 확정/기본안/미정을 구분해 `결정-기록.md`에 적는다. 작가의 의견으로 제안이 바뀐 곳도 기록한다 |
