# 하루 영수증 명세

작성일 2026-11-07 · 상태: **초안** (작가 요청으로 1차 구현, 형식은 확인 대기) · 근거: `기반층-명세.md` 0-4(사건 봉투)·3(기록), `구현-계획.md` 21, 원 프로젝트 `make-bio-database`의 `judicial/log_audit.js`(사건 사슬)·`judicial/process_report.js`(과정 보고서·무결성 증명서)·`judicial/attestation.js`(정준 JSON 다이제스트)

하루씨의 하루를 **데이터로 남긴다.** 엔진이 낸 사건 기록을 하루 단위로 끊어 영수증을 찍는다. 사건은 사건끼리, 하루는 하루끼리 이어진다. 영수증은 엔진을 다시 돌리지 않고 영수증만으로 검증된다.

---

## 1. 정의

| 말 | 뜻 |
|---|---|
| 영수증 | 하루 한 장. 그날의 사건 목록, 집계, 마감, 봉인 (`src/core/receipt.ts`의 `Receipt`) |
| 날 | 절대 분 `t`의 날 = `floor(t / 1440) + 1`. 영수증의 범위는 `[from, to)` |
| 실행 정보 (`run`) | 시나리오 경로·시나리오 sha256·콘텐츠(저장소 + 사전) sha256·seed·시작·끝 |
| 기원 고리 | `해시("genesis\n" + 정준(run))`. 첫 사건과 첫 영수증이 문다 |
| 고리 (`root`) | 사건마다 `해시(직전 고리 + "\n" + 정준(사건))`. 직전 고리는 `prev` |
| 봉인 (`seal`) | 영수증마다 `해시(앞 봉인 + "\n" + 정준(봉인을 뺀 영수증))`. 앞 봉인은 `prev_seal` |
| 마감 (`close`) | 그날까지의 사건을 처음부터 접은 결과: 개체 목록, 바뀐 세계 상태, 인물의 앎, 넘어가는 예약 |
| 정준 JSON | 키를 정렬한 JSON. 같은 값이면 같은 글자 |

## 2. 규칙

1. **엔진에서 정보를 빼는 길은 사건 기록 하나다.** 영수증은 `runScenario`가 낸 `log`만 읽는다. 엔진 내부(판·층)를 읽지 않고, 엔진을 돌리지도 않는다 (원 프로젝트에서 사법부가 행정부의 원자료만 받는 것과 같다).
2. **사건은 이어진다.** 모든 사건이 빠짐없이 seq 순서대로 한 번씩 들어가고, 고리는 날을 넘어서도 이어진다. 다음 날의 `head_in`은 앞날 마지막 사건의 고리다.
3. **하루는 이어진다.** 실행의 첫날부터 끝날까지 하루 한 장씩 찍는다. 사건이 없는 날도 찍는다. 영수증은 앞 영수증의 봉인을 문다.
4. **원인은 사건의 `cause`를 그대로 적는다.** 원인이 앞날의 사건이면 `cause_day`에 그 날을 적는다. 엔진이 원인을 적지 않은 사건은 원인 없이 찍는다 (지어내지 않는다).
5. **파생값은 검증된다.** 집계·마감·`cause_day`는 사건에서 계산되고, 검증이 사건만으로 다시 계산해 맞춰 본다. 손으로 고치면 잡힌다.
6. **찍을 때 어긋나면 찍지 않는다.** 시각이 거꾸로 가거나, 상태 변화의 `from`이 앞의 상태와 다르면 `ReceiptError`.
7. **해시 함수는 인자로 받는다.** 코어는 입출력 모듈을 쓰지 않는다. 노드 쪽(`clerk.ts`)이 sha256을 넘긴다.
8. **글자판은 표시만 한다.** 이름은 정의 저장소와 사전에서 가져오고, 해시에 들어가지 않는다. 사전에 없는 사건 유형은 유형 이름과 data를 그대로 보인다.
9. **쓰기는 서기만 한다.** `receipts/<시나리오>/day-NNN.json`(원본)과 `.txt`(글자판). 쓰기 전에 검증한다. 실행 결과라서 git에 넣지 않는다 (`saves/`와 같다).

## 3. 검증 (`verifyReceipts`)

| 확인 | 어기면 |
|---|---|
| 형식·버전 | 형식이 아니다 |
| 실행 정보가 모든 장에서 같음 | 다른 실행의 영수증이 섞임 |
| 날이 1씩 이어지고 범위가 날 번호와 맞음 | 날이 이어지지 않는다 |
| `prev_seal` = 앞 봉인 (첫 장은 기원 고리) | 하루 사슬이 끊김 |
| `head_in`·`prev` = 직전 고리 | 사건 사슬이 끊김 |
| seq가 L000001부터 빈틈없음 | 빠지거나 끼운 사건 |
| 고리 재계산 | 사건 내용이 바뀜 |
| 시각이 날 범위 안, 거꾸로 가지 않음 | 범위 밖 / 거꾸로 |
| 사건 유형이 정한 근거 참조(`via`)를 가짐 (7장) | via가 필요하다 / via 종류가 맞지 않는다 |
| 원인이 앞에 있음, `cause_day`가 맞음 | 원인이 앞에 없다 / 날 넘는 원인 표시가 맞지 않는다 |
| 집계·마감 재계산 | 사건과 맞지 않는다 |
| 봉인 재계산 | 영수증이 찍힌 뒤 바뀜 |

`receipt <시나리오> --check`는 여기에 더해 **다시 돌려 찍은 영수증과 봉인이 같은지** 본다 (결정론, 엔진·데이터가 바뀌었는지).

거부 사례는 `test/receipt.test.ts`의 "거부:" 시험이다 (사건 고침·빼기, 날 빼기·바꾸기, 집계·마감 고침, 봉인 고침, 실행 섞임, 날 넘는 원인 표시). 패치 거부 말뭉치(`test/fixtures/rejections/`)는 패치만 받으므로 여기에 넣지 않았다.

## 6. 미정

1. **원인이 비어 있는 사건.** 영수증에서 걸러 `docs/원인-빈칸.md`로 내고, 항목마다 원인을 조사해 `data/limitations.json`(한계 등록부, `docs/한계-등록부.md`로 생성)에 **설계 오류 / 기능 부재 / 원천**으로 나눠 적는다. 엔진을 고쳐 빈칸이 0건이 되면 그 항목의 상태가 해결로 계산된다. (2026-11-07: LIM007은 결정으로 해소 — 7장. LIM005는 법칙이 원인이므로 원천으로 재분류.) 등록 안 된 빈칸이 생기면 시험이 실패한다 (`gaps --check`).
2. **영수증을 git에 남길지.** 지금은 실행 결과라 넣지 않는다. 시연용 한 벌을 남긴다면 골든 트레이스처럼 `--check`를 시험에 걸어야 낡지 않는다.
3. **하루의 경계.** 지금은 게임 분 0시. 시계의 하루 경계(실제 시각 04:00)나 잠에서 깰 때로 끊을지.
4. **마감에 무엇을 넣을지.** 지금은 기록에 나온 것만 (살 때 그대로인 상태는 기록에 없으면 빠진다). 컨디션·습관이 생기면 더한다.

## 7. 사건의 근거 `via` (2026-11-07)

사건은 두 가지 이유를 따로 적는다.

| 칸 | 뜻 | 몇 개 |
|---|---|---|
| `cause` | 직전의 어떤 **사건**이 일으켰나 (조건을 마지막으로 채운 사건) | 하나 |
| `data.via` | 어떤 **규칙·행동·법칙·감각**이 만들었나 | 하나 |

근거가 여럿인 조건(규칙의 `on`, 행동의 `needs`)은 via가 가리키는 정의 안에 있다. 어느 값이 거기 맞았는지는 정의와 기록에서 다시 계산한다. 그래서 `cause`를 목록으로 바꾸지 않는다 (한계 LIM007 해소).

모양은 `정의 번호/종류/키`다 (원 프로젝트에서 단계가 "규칙 참조와 대상"만 가지는 것과 같다).

| 종류 | 가리키는 것 | 예 | 쓰는 사건 |
|---|---|---|---|
| `rule` | 정의의 규칙 (통로에서 만든 번짐 규칙 포함) | `PLC000002/rule/odor_thicken` | 지연 예약·발화·취소 |
| `offer` | 정의가 내놓는 행동 | `PLC000002/offer/inspect` | 행동 고름·끝, 살펴서 안 것 |
| `progress` | 그 정의의 인스턴스에 걸린 진행 법칙 (특징) | `OBJ000003/progress/decay` | 단계 진행 |
| `sense` | 인물 정의의 감각 | `CHR000001/sense/smell` | 저절로 느낀 것·없어진 것 |

- 어느 유형이 어떤 종류를 가져야 하는지는 사전 `event_type`의 `via_kinds`가 정한다 (8개 유형). 정하지 않은 유형(`state_changed`, `instance_created`)은 via를 갖지 않는다. 상태 변화의 근거는 `cause`가 가리키는 사건의 via로 찾는다.
- **기록이 받지 않는다**: via가 없거나 모양·종류가 틀리면 `EventLog`가 그 사건을 거부한다 (`checkData`). 엔진이 근거를 빠뜨리면 그 자리에서 터진다.
- **영수증 검증**도 같은 규칙으로 본다. 지워지거나 종류가 바뀐 via는 봉인을 다시 맞춰도 잡힌다.
- **실제로 있는 것을 가리키는가**는 `viaResolver`(저장소와 사전에서 찾기)가 확인한다. 첫 주의 via 144건이 모두 있는 규칙·행동·법칙·감각을 가리킨다 (시험).
- 이전에는 지연 사건이 `rule`, 행동 사건이 `offer`로 제각각 적었다. 하나의 칸 `via`로 합쳤다 (골든 트레이스가 이 이름 바꾸기만큼 달라졌다).
- 다음 일 (구현 계획 21R): **영수증 감사** — via가 가리키는 규칙의 `on`/`emits`/`effect`와 사건의 변화가 맞는지 정의에서 다시 계산한다.

## 8. 영수증 감사 (2026-11-07)

영수증 검증(3장)은 기록이 **바뀌지 않았는지**를 본다. 감사는 기록이 **정의대로인지**를 본다. 사건 기록과 정의 저장소만 받고 엔진은 돌리지 않는다 (`src/core/audit.ts`). 어떤 규칙이 있나는 엔진과 같은 목록(`allRules`)을 쓰고, 언제 어떻게 도는지는 감사가 다시 계산한다. 둘이 어긋나면 한쪽의 버그다.

| 검사 | 확인하는 것 |
|---|---|
| rule | 사건의 `via`가 그 개체에 걸리는 규칙이다 (종류에서 물려받은 규칙·번짐 규칙 포함) |
| timing | 예약의 발화 시각 = 예약 시각 + 규칙의 지연. 발화·취소는 예약 시각에, 예약마다 하나. 규칙 × 개체의 예약은 동시에 하나 |
| holds | 예약할 때 조건이 맞고 결과가 아직 아님. 발화는 조건이 맞을 때, 취소는 풀렸을 때 (같은 시각 발화들은 묶음 직전의 값을 읽는다) |
| effects | 발화·행동 끝·진행·살 때의 상태 **바로 뒤**에, 정의가 요구하는 상태 변화가 빠짐도 덤도 없이 그 순서로 이어진다 |
| state | 상태 변화의 `from`이 지금 단계. 원인은 처음 상태·발화·행동 끝·진행뿐이고, 원인 없는 변화는 시나리오의 처음 설정 시각까지만 |
| progress | 진행은 사다리를 올라가고, 잠긴 칸이 아니며, 그 물건에 그 법칙이 있다 |
| action | 행동이 그 개체가 내놓는 것이고, 동사·끝나는 시각(= 고른 시각 + 걸리는 분)·끝난 기록이 맞다 |
| awareness | 저절로 느낀 것은 감각의 알아채는 칸 이상이고 세계의 단계와 같다. 살펴서 안 것은 그 행동이 끝난 뒤이고 이해함이다. 인지 단계는 오르기만 한다 |

- 명령: `audit [시나리오]`. `receipt --check`가 영수증 검증과 함께 돌린다.
- **하지 않는 것** (한계 등록부): 진행이 경계를 넘는 시각(LIM013), 행동을 고른 이유(LIM014), 있어야 할 예약이 빠진 것(LIM015).
- 시험: 두 시나리오와 무작위 시나리오 40개가 위반 0, 사건을 하나씩 망가뜨린 17가지가 모두 잡힌다. 구현 중 무작위 900개를 더 돌렸다. 어긋남은 감사 쪽 버그 1건(같은 시각 묶음의 값을 시각이 바뀌어도 쓰던 것)이었고 엔진 쪽 버그는 나오지 않았다.
