# 보고서 형식과 관리 규칙

작성일 2026-11-05 · 상태: **제안** (작가 확인 대기 항목은 10장). 문서가 늘어서 종류와 상태가 섞이기 시작했다. 이 문서는 **문서 종류, 머리 표기, 상태 어휘, 본문 뼈대, 관리 규칙**을 정한다. 현재 문서 목록은 `보고서-목록.md`에 있다.

---

## 1. 왜 정하나

- 이 프로젝트는 AI와 함께 만든다. 문서가 많아지면 어느 것이 **결정**이고 어느 것이 **제안**인지, 어느 것이 **낡았는지**를 알 수 없게 된다.
- 지금도 같은 내용이 여러 곳에 있다 (데이터 입력 설계 보고서와 데이터 형식의 재질·특성). 결정이 보고서 안에 묻힌 곳도 있다.
- 원칙: **결정은 한 곳에만, 근거는 보고서에, 규칙은 명세에.**

## 2. 문서 종류 (10종)

| 종류 | 묻는 것 | 결정하는가 | 예 |
|---|---|---|---|
| 기획 | 무엇을, 왜 | 방향을 적는다 | `기획보고서-v3.md` |
| 계획 | 어떻게, 언제, 무엇으로 검증 | 순서를 적는다 | `개발-계획서.md`, `구현-계획.md` |
| 결정 | 무엇이 정해졌나 | **예. 유일한 원본** | `결정-기록.md` |
| 명세 | 규칙과 형식이 정확히 무엇인가 | 확정된 규칙을 적는다 | `품질판-명세.md`, `데이터-형식.md` |
| 설계 | 어떻게 만들면 좋은가 (대안, 제안) | **아니오.** 제안한다 | `축-상호작용-설계.md` |
| 분석 | 지금 상태가 어떤가, 무엇이 문제인가 | **아니오.** 보고한다 | `층-비교.md`, `구현-난이도-병목-보고서.md` |
| 조사 | 바깥에 무엇이 있나 | 아니오 | `선행-사례.md` |
| 예시 | 이 형식으로 쓰면 이렇게 된다 | 아니오 (작가가 고친다) | `예시-사과.md` |
| 자동 생성 | 현재 데이터에서 계산한 표 | 아니오. 손으로 고치지 않는다 | `자동생성-부록.md`, 패치 보고서 |
| 관리 | 문서 자체를 관리한다 | — | `보고서-형식.md`, `보고서-목록.md` |

보관(`docs/보관/`)은 종류가 아니라 **위치**다. 완전히 대체된 문서만 간다.

## 3. 머리 표기 (모든 문서 첫 줄과 둘째 단락)

```
# 제목 (종류가 이름에 드러나게)

작성일 YYYY-MM-DD · 상태: **초안** · 근거: `다른-문서.md` 3장, `또다른-문서.md`
```

- **작성일**: 필수. 갱신 이력은 git에서 본다 (머리에 갱신일을 따로 적지 않는다).
- **상태**: 필수. 4장의 어휘 중 하나.
- **근거**: 이 문서가 기대는 문서와 절. 없으면 생략.
- **대체**: 다른 문서에 대체되면 `대체: 새-문서.md` 한 줄을 머리 아래에 더한다.

## 4. 상태 어휘

| 상태 | 뜻 | 다음 |
|---|---|---|
| 초안 | 쓰는 중이거나 작가 확인 전 | 고정안 또는 폐기 |
| 제안 | 선택지를 내놓았고 작가의 선택을 기다림 | 결정 기록에 반영되면 고정안, 아니면 폐기 |
| 분석 | 지금 상태를 보고한 것. 결정하지 않음 | 근거가 낡으면 정정 안내를 단다 |
| 고정안 | 작가가 정한 규칙. 구현이 따른다 | 명세로 승격하거나 대체됨 |
| 대체됨 | 일부 또는 전부를 새 문서가 대신함 | 전부면 보관으로 |
| 자동 생성 | 도구가 만든다 | — |
| 보관 | 대체되어 읽을 필요가 없음 | — |

한 문서 안의 절마다 **확정 / 기본안 / 잠정** 표시를 쓰는 경우는 그대로 둔다 (`결정-기록.md`, `데이터-형식.md`).

## 5. 종류별 본문 뼈대

| 종류 | 순서 |
|---|---|
| 분석 | 결론 → 근거(**읽은 범위와 읽지 않은 범위**) → 문제 목록 → 권장 → 작가에게 묻는 것 |
| 설계 | 문제 → 제안 → 결정 사항(표) → 영향 → 구현 목록 → 열린 질문 |
| 명세 | 정의 → 규칙 → 시험(어떻게 확인하나) → 구현 상태(구현/확정/잠정) → 미정 |
| 계획 | 작업 표 (번호, 작업, 자리, 끝나는 조건, 상태) |
| 결정 | 행 단위: 항목 \| 결정 \| 상태 \| 반영 |

- 결론은 **맨 앞**에 둔다. 읽는 사람이 첫 화면에서 판단할 수 있어야 한다.
- 모르는 것과 확인하지 못한 것은 **적는다** (CLAUDE.md의 보고 규칙과 같음).
- 임시값은 `tuned:false`, 가정은 가정이라고 쓴다.

## 6. 사용자 보고 (채팅)

- 결론을 먼저, 그다음 근거와 결정이 필요한 항목을 번호로 쓴다.
- 확인한 것과 **확인하지 못한 것**을 구분한다.
- 표로 쓸 수 있는 것은 표로 쓴다. 긴 설명은 문서로 두고 위치를 알려 준다.
- 원 프로젝트(`make-bio-database`)는 사용자 보고를 **같은 네 칸 표**(Scope · Why · Impact · Verification)로 강제한다. 이 프로젝트는 아직 강제하지 않는다 (10장 질문 3).

## 7. 자동 생성 보고서

| 이름 | 만드는 곳 | 내용 | 보관 |
|---|---|---|---|
| **패치 보고서** | `src/core/report.ts`, 명령 `validate`·`merge` | **이유** · 범위(추가·수정·이름 해석) · 영향(바뀐 정의를 가리키는 곳, 새 규칙 사슬 간선) · 검증(관문 통과 여부, 오류·경고 수) · 결과 | 화면에 출력. 저장하지 않는다 |
| **자동 생성 부록** | `src/core/appendix.ts`, 명령 `appendix` | 정의 표, 규칙 사슬, 사전 규모 | `docs/자동생성-부록.md` (낡으면 시험이 실패) |
| 하루 과정 보고서 | 구현 계획 21 (예정) | 요약, 하루 전개, 컨디션 추이, 인과 추적, 무결성 증명서 | 미구현 |
| 제한 요인 분류 | 구현 계획 21A (예정) | 하루가 왜 이렇게 흘렀나 | 미구현 |

- 패치 보고서는 지금 **저장되지 않는다.** 원 프로젝트는 패치 기록(`data/patches/`)에 `report`를 저장해 나중에 `report <기록>`으로 다시 본다. 이 프로젝트에도 필요한지는 10장 질문 2.

## 8. 관리 규칙

1. **새 문서는 같은 커밋에서 `보고서-목록.md`에 올린다.** 빠지면 시험이 실패한다.
2. **상태를 바꾸면 머리와 목록을 같은 커밋에서 고친다.**
3. **결정은 `결정-기록.md`에만** 행으로 남긴다. 보고서와 명세의 "확정 결정" 절은 그 행을 가리킨다 (복사하지 않는다).
4. **대체되면** 옛 문서 머리에 `대체:` 한 줄을 달고 목록의 상태를 "대체됨"으로 바꾼다. 완전히 대체되면 `보관/`으로 옮긴다.
5. **문서는 전체를 다시 쓰지 않는다.** 해당 절만 고친다 (원 프로젝트의 규칙).
6. 이름은 한국어로 짓고, 종류가 드러나게 한다 (`-명세`, `-계획서`, `-기록`, `-보고서`). 분석 문서는 `-보고서`나 `-비교`처럼 분석임이 이름에 보이게 한다.
7. 확인 대기 질문은 문서 끝 절에 모은다. 어디에 있는지는 `보고서-목록.md` 5장이 안내한다.

## 9. 원 프로젝트(`make-bio-database`)의 보고서 형식 — 참고

| 형식 | 위치 | 내용 | 이 프로젝트에서 |
|---|---|---|---|
| `CHANGES.md` | 루트 | 코드·형식 변경 한 행씩 (Scope · Why · Impact · Verification). 맨 위가 최신, 고치거나 지우지 않음 | 도입 여부 미정 (10장 1) |
| Patch Report | 패치 기록의 `report` | Scope · Why · Impact · Verification를 계산해 저장 | 출력만 있음 |
| `docs/reports/날짜-주제.md` | `docs/reports/` | 분석·검증 보고서 14건 (예: `2026-10-15-gate-a-prime-tap-mhc1.md`) | 분석 문서에 날짜·주제 이름 규칙 후보 |
| 과정 보고서 | `fate ... --report` | 요약, 변곡점, 구간표, 무결성 증명서, 인과 추적 | 구현 계획 21 (예정) |
| `limitations.md` | 루트 | 실패·우회·추정·단순화를 한계로 등록 | 지금은 문서 안에 흩어져 있음 |
| 사용자 보고 | 채팅 | 같은 네 칸 표, 산문 요약 금지 | 6장 |

## 10. 작가 확인 (권장안 포함)

1. **변경 기록(`CHANGES.md` 같은 한 곳)을 도입할까요?** 지금은 변경 이유가 커밋 메시지와 결정 기록에 나뉘어 있다. 권장: 코드·형식 변경만 한 행씩 남기는 `CHANGES.md`를 도입하고, 결정 기록은 결정만 남긴다.
2. **패치 보고서를 저장할까요?** 권장: 패치 기록과 같이 저장 (원 프로젝트 방식). 다시 볼 수 있다.
3. **사용자 보고를 네 칸 표로 강제할까요?** 권장: 아니오. 결론 먼저, 확인한 것과 못 한 것 구분만 강제한다.
4. **분석 문서의 이름 규칙** (`날짜-주제.md`)을 쓸까요? 권장: 지금은 이름 규칙(6장)만. 분석이 10건을 넘으면 `docs/분석/`으로 옮긴다.
